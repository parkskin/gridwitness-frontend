# GridWitness AI 원인분석 동작과 화면 설계 기준

이 문서는 GridWitness의 파형 분석과 현장 도우미가 실제로 어떤 입력을 받아 어떤 결과를 내는지 설명합니다. 페이지에서는 모델의 이벤트 유형 판단, 측정 파형에서 직접 계산한 사실, 아직 확인하지 못한 물리적 원인을 구분해야 합니다. 현재 모델은 고장 원인을 확정하거나 보호 동작을 지시하지 않습니다.

## 먼저 알아둘 점

GridWitness의 “AI 원인분석”은 현재 **파형 사건 유형 분류와 근거 설명**을 제공합니다. 사건 유형은 예를 들어 학습 데이터의 특정 유형에 파형이 얼마나 가까운지를 나타냅니다. “케이블 단선”, “접촉 불량”처럼 설비의 물리적 원인을 현장에서 확정하는 기능과는 다릅니다. 모델 점수도 정답일 확률로 해석하면 안 됩니다.

## 시스템에서 분석이 만들어지는 순서

1. **사건 등록**: 브라우저가 파형 파일과 데이터셋 ID, 샘플링 주파수, 계통 주파수 등 메타데이터를 API에 등록합니다. 서버는 원본 파일과 해시를 보관합니다.
2. **입력 검증**: 분석 전에 채널·표본 수·값·메타데이터를 검사합니다. 잘못된 입력은 거부되고, 제한된 입력은 범위를 표시합니다. 검증을 통과하지 못하면 분류 결과를 만들지 않습니다.
3. **모델 선택**: 서버는 데이터셋 ID에 `xiong`이 포함되면 CN, `oscgrid`가 포함되면 RU 모델을 선택합니다. 알 수 없는 데이터셋을 임의로 다른 나라 모델에 넣지 않고 분석을 보류합니다.
4. **특징 계산과 분류**: `gw_ai` 분석기가 원본 파형을 계약된 채널·표본 규격에 맞춰 처리하고, 해당 모델이 학습한 이벤트 라벨을 점수 순으로 계산합니다. 요청 메타데이터, 모델/계약 버전, 파일 해시, 특징 근거를 결과에 포함합니다.
5. **보류 판단**: 학습 범위를 벗어난 정도(OOD), 1순위 점수, 1·2순위 차이를 기준과 비교합니다. 하나라도 기준을 넘지 못하면 1순위 라벨을 확정하지 않고 보류 사유를 반환합니다. 입력 거부, 모델 부재, 국가/도메인 불일치, 모델 오류도 별도 상태로 남깁니다.
6. **저장과 화면 표시**: API는 검증 ID, 분석 상태, 특징, 분류, 보류 사유, 전처리 버전, 모델 버전을 기록합니다. 화면은 이 응답을 표시하며, 서버가 결과를 주지 않으면 성공한 분석처럼 꾸미지 않고 보류/오류로 처리해야 합니다.

```text
원본 파형 + 사건 메타데이터
          ↓
입력 검증 ── 실패 → 거부/제한 사유 표시
          ↓ 통과
데이터셋 도메인에 맞는 모델 선택 ── 모델 없음/불일치 → 보류
          ↓
파형 특징 계산 → 이벤트 유형 점수 + OOD/분리도 검사
          ↓
확정 가능한 유형 또는 판단 보류
          ↓
API에 버전·근거·상태 저장 → 웹에서 결과와 한계 표시
```

## 화면에서 서로 다른 세 가지 정보를 분리해 보여주기

### 1. 모델의 이벤트 유형 판단

이 영역은 예측 라벨, 점수 순위, 모델/계약 버전, 분석 상태를 보여줍니다. 점수는 분류 모델의 출력값입니다. **“확률”, “신뢰도 87%”, “고장일 가능성 87%”처럼 쓰지 마세요.** 점수가 임계값을 통과하지 못했거나 입력 범위가 맞지 않으면 라벨 대신 “판단 보류”와 보류 사유를 보여줍니다.

CN 모델은 정상·개폐 라벨을 포함하지 않는 데이터셋 계약이므로 CN 결과만으로 정상/고장을 탐지할 수 없습니다. RU는 OscGrid 데이터의 이벤트 유형 분류로, 국내 현장 성능을 입증한 결과가 아닙니다. 화면에는 데이터셋 출처와 적용 범위를 항상 붙입니다.

### 2. 파형에서 직접 계산한 관측 사실

별도 계산기는 기록 초반 1주기를 기준으로 사건 시작점을 찾고, 각 상의 전류·전압 RMS 변화, 최대 변화 상, 영상전류(입력에 있을 때), 기록 끝까지 변화가 지속되는지, 기록 안에서 복귀가 관측됐는지를 계산할 수 있습니다. 이 값은 모델 라벨과 다른 종류의 정보입니다.

예시 표현:

- “사건 시작: 기록 후 0.42초, 샘플 4,200”
- “B상 전류 RMS: 기준 3.1 A → 사건 직후 7.8 A”
- “기록 마지막까지 변화가 지속됨; 복귀는 이 기록에서 확인되지 않음”
- “비교 기준은 기록 초반입니다. 기록 시작 전 상태는 알 수 없습니다.”

이는 파형 내 변화의 설명이지, “B상 케이블 접촉 불량 확정”과 같은 물리적 원인 진단이 아닙니다. 센서 위치·설치 상태·교정·계통 운전 조건이 확인되지 않으면 설비 위치나 원인을 추정해서는 안 됩니다.

### 3. LLM 현장 도우미

LLM은 분석기를 대신해 파형을 판정하거나 고장 원인을 새로 계산하지 않습니다. 서버가 제공한 사건/마을 근거 중 질문에 맞는 근거를 고르고, 그 값만 사용해 문장으로 설명합니다. 구현은 구조화된 응답에서 근거 ID를 확인하고, 실제 값과 인용은 서버가 선택된 근거에서 구성합니다. 근거가 부족하거나 출력 형식이 맞지 않으면 답을 보류하거나 규칙 응답으로 대체합니다. 설비 제어 요청은 거절합니다.

따라서 화면은 “분류 결과”와 “AI 설명”을 구분하고, 설명 옆에 출처 근거를 펼쳐 볼 수 있게 해야 합니다. LLM의 자연스러운 문장 자체를 분석의 증거로 취급하지 않습니다.

## 점수와 상태를 표시하는 기준

| API 상태 | 사용자에게 보일 문구 | 페이지 동작 |
|---|---|---|
| `ok` | 유형 분류 완료 | 라벨·점수 순위·근거·모델 버전을 표시하되 점수를 확률로 표기하지 않음 |
| `abstained` | 판단 보류 | 라벨을 결론처럼 강조하지 않고 보류 이유와 추가로 필요한 정보를 표시 |
| `rejected` | 분석 불가 | 입력 오류와 수정 방법 표시, 분류 결과 영역은 비워 둠 |
| API/모델 오류 | 분석 서버 응답 확인 필요 | 오래된 결과를 새 결과처럼 보이지 않게 시간과 상태를 구분 |

API 응답의 `features.gw_ai.evidence`에는 대표 특징, 계산 방법, 1순위 점수, 1·2순위 차, OOD 비율과 임계값이 포함될 수 있습니다. 설명 페이지는 특징 이름만 나열하지 말고 단위·계산 의미·해석 한계를 함께 제공해야 합니다. SHAP 기여도는 모델 내부의 예측 기여 설명이지 전기적 인과관계 증명이 아닙니다.

## 페이지 구성 제안

1. **상단 요약**: 분석 상태, 판정/보류 배지, 사건 시각, 분석 요청 시각, 데이터 출처, 검토 상태.
2. **파형 타임라인**: 원본 파형과 사건 시작점을 겹쳐 표시하고, 확대·상별 표시·기준 구간과 사건 구간 선택을 지원.
3. **관측 사실 카드**: 상별 전압·전류 변화, 불평형/영상 성분(입력이 있을 때), 지속/복귀, 계산 방법과 비교 구간.
4. **모델 판단 카드**: 이벤트 라벨과 점수 순위, 보류 기준 통과 여부, 학습 범위 밖 여부, 모델/데이터셋 버전. 점수는 “모델 점수”로 명시.
5. **판단 근거와 한계**: 주요 특징, 선택된 데이터/범위, 적용 한계, 확인하지 못한 정보.
6. **현장 도우미**: 질문·답변과 함께 사용한 근거를 표시. LLM/규칙 답변 모드, 답변 시각, 인용 근거를 구분.
7. **사람의 검토와 이력**: 작업자 판단, 확인된 원인, 추가 조사 결과를 AI 결과와 분리해 기록. 수정 전 결과도 감사 이력에서 추적 가능.

## 현재 확인된 제한과 개발 우선순위

- 이 모델의 출력은 이벤트 유형 분류이며 물리적 고장 원인·고장 위치·복구 조치를 확정하지 않습니다.
- CN/RU 학습 데이터의 라벨과 운영 도메인이 국내 한전 FRTU 사건을 대표한다고 확인된 상태가 아닙니다. 실제 한전 데이터의 라벨 검토와 외부 검증이 필요합니다.
- CN에는 정상·개폐 유형이 없으므로 “정상/고장” 판정으로 오해되지 않게 해야 합니다. 개폐·정상 사건을 포함한 학습/평가가 필요합니다.
- 보류 임계값은 주어진 학습/검증 데이터에 대한 선택 기준입니다. 현장 성능 보증이나 확률 보정으로 볼 수 없습니다.
- 공식 Ollama 카탈로그는 3B를 Qwen Research License로, 7B를 Apache-2.0으로 표시합니다. 이에 따라 운영 GPU 서버에 7B를 추가하고, GPU 직접 호출과 임시 API 인스턴스의 구조화된 근거 선택을 확인한 뒤 운영 모델을 `qwen2.5:7b`로 바꿨습니다. 운영 API의 실제 답변도 `answer_mode=llm`, 모델 `qwen2.5:7b`, 근거 1건으로 확인했습니다. 이는 연결·응답 경로의 스모크 확인이지, 174문항 현장 평가나 국내 계통 정확도 검증을 마쳤다는 뜻은 아닙니다.
- 2026-11-11 KST 직접 시리얼 확인에서 Arduino UNO(COM19)는 연결됐지만 INA219 0x40만 응답했고 0x41은 `NOT FOUND`였습니다. 측정 줄에는 전체 `v`, `i`, `relay`, `ch`만 있어 주택/가로등 구간 실측값은 없습니다. 당시 전체 측정은 약 3.711 V, 0.034 A였습니다. 두 구간 측정, 센서 교정, 최신 웹의 Web Serial 장시간 안정성은 아직 확인하지 못했습니다. 실제 장치와 시뮬레이터를 다른 출처 배지로 표시하고, 구간값이 없으면 비어 있거나 “측정 불가”로 보여 주세요.
- 운영 API에는 `SERIAL` 사건 96건이 저장돼 있으며, 모두 원시 표본 260개입니다. 원인 신호 `src` 기준으로 명령(`cmd`) 사건 20건과 자동 감지(`auto`) 사건 76건이 별도 보존돼 있습니다. 최신 확인 사건 #34는 자동 감지이고 분류는 `WITHHELD`였습니다. 1순위는 순간 접촉 불량, 점수 0.4925, 1·2순위 차 0.1967로 기준을 통과하지 못했습니다. 이것은 순간 접촉 불량 확정이 아닙니다. 직전 저장 사건 #33은 260표본, `ANSWERED`였으므로 UI는 사건별 판정/보류 상태를 각각 유지해야 합니다.
- AI 결과는 보호계전, 차단기 제어, 작업 허가 또는 안전 판단을 자동 수행하지 않습니다. 현장 담당자 검토와 별도 안전 절차가 필요합니다.

## 2026-11-11 챗봇·저장 데이터 재검증

### Qwen 2.5:7B 현장 챗봇 평가

- 실제 GPU VM의 Ollama `qwen2.5:7b`에 SSH 터널로 연결해 평가했습니다. 질문 근거는 운영 API에서 읽은 실제 COMPLETED, WITHHELD, NONE 사건 컨텍스트 3건이며, 운영 DB에는 POST/write 요청을 보내지 않았습니다.
- 평가기는 현장 질문 평가 세트의 dev 90문항을 세 상태별로 실행해 270개 응답을 확인했습니다. 모델 근거가 실제 사건에 없는 학습 데이터·정확도·한계 질문은 “답변 가능” 기대값에서 제외하고, 올바른 기대를 “보류”로 보정했습니다.
- 최종 후보 코드에서 응답 상태 270/270, 질문에 맞는 근거 그룹 270/270, 존재하지 않는 근거 ID 0건이었습니다. 24건은 실제 LLM 응답, 246건은 안전·범위·근거 완전성 규칙에 따른 응답 또는 대체였습니다. 따라서 챗봇은 기본 사건 질문에 응답하지만 모든 질문이 LLM 생성 답변으로 처리되는 것은 아닙니다.
- 수정 전 실제 LLM에서 분석 보류 사건의 “왜 그렇게 봤어?”를 사람 검토 질문으로 혼동해 답한 사례와, 저장되지 않은 학습 데이터/정확도 근거 대신 `source.*` 또는 분석 근거를 선택한 사례가 재현됐습니다. 후보 코드는 보류 분석의 결론·근거 승격을 차단하고, 학습 데이터·정확도·한계가 사건 근거에 없으면 LLM을 호출하지 않으며, 질문에 필수인 근거 ID가 빠지면 규칙 답으로 대체합니다. 기본 결과 질문에는 결과에 직접 필요한 근거를 요구하고, 질문하지 않은 검토 이력이나 다른 근거 전체를 강제하지 않습니다.
- 이 코드 수정은 API PR [#17](https://github.com/sunwoo162/gridwitness-api/pull/17)로 병합됐고, API main 커밋 `26b8d842d6b1c339693d114445e12bc969835da9`를 운영 배포했습니다. 배포 전 코드와 SQLite DB를 각각 백업하고, 운영 DB 복사본 스테이지에서 검증한 뒤 systemd를 재시작했습니다.
- 배포 스테이지 API를 통해 실제 세 상태 사건에 7개 대표 질문을 보냈습니다. 답변 상태는 기대와 일치했고, 완료 사건의 근거 질문은 `qwen2.5:7b`가 답했습니다. 보류/미실행 결과와 근거 질문은 규칙 답으로 보류했고, 학습 데이터가 없는 질문도 보류했습니다. 스테이지에서 7개 turn 모두 사용자·도우미 메시지 각 1개, 비어 있지 않은 본문으로 저장됐고, 같은 turn ID 재시도는 같은 응답 ID를 돌려줬습니다.
- 운영 배포 후 “그렇게 판단한 근거는 뭐야?”를 시연 사건에서 실제 Qwen 2.5:7B로 질의해 `answer_mode=llm`, 근거 인용을 확인했습니다. 사용자·도우미 2개 메시지가 저장됐고 `assistant.answered` 감사 이벤트가 1건 추가됐습니다. 감사 payload에서 `message_id`가 저장 메시지와 연결되고, `answer_mode`, `llm_model`, 근거 ID 7개, `client_turn_id`가 보존되는 것까지 확인했습니다. 재시도는 같은 메시지 ID였으며 검증 대화는 reset해 아카이브에 보관했습니다. 운영 `/health`는 DB ready, capabilities는 인증 필수·Qwen available, systemd는 active, SQLite `integrity_check=ok`입니다. 운영 DB에 기록된 검증 대화는 이 시연 사건의 아카이브 대화에만 남아 있고 활성 대화는 비어 있습니다.
