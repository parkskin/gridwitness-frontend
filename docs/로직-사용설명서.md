# GridWitness 로직 사용 설명서

화면(React)을 몰라도 `src/lib/`·`src/api/`의 로직만 가져다 쓸 수 있게 정리한 문서입니다.
기준 코드: ParksKin 프론트 저장소 `main` (2026-11-10, `a54e534`). 함수 이름·시그니처는 코드와 대조했습니다.

## 0. 먼저 알아둘 것

**데이터 3종은 절대 섞지 않습니다.** 단위·주기·규모·목적이 달라서입니다.

| 구분 | 데이터 | 코드 위치 | 하는 일 |
|---|---|---|---|
| IoT | Arduino + INA219 (설계는 2개; 감지된 센서만 구간 계측, 5V DC 전압·전류) | `lib/village.ts`, `lib/serial.ts`, `lib/hardware.ts` | 이상 탐지 (규칙 기반) |
| CN 파형 | 1312×7, 4096Hz, 50Hz (Ia Ib Ic In Va Vb Vc) | `lib/waveform.ts`, `lib/comtrade.ts`, `lib/faultAnalysis.ts`, `api/` | 입력 검사·특징 계산·서버 분류 |
| RU 파형 | 512×5, 1600Hz, 50Hz (Ia Ic Va Vb Vc) | 같은 파형 처리 경로, RU 입력 계약 | 실제 5채널 보존·입력 검사·서버 분류 |
| 공공데이터 | 한전 지역·시간대별 사용량 | `lib/publicData.ts` | 패턴 분석, 마을 부하 시나리오 (학습 안 함) |

- IoT 이벤트는 DC 기록 그대로 `IotCase`로 저장합니다. 교류 파형으로 변환하지 않습니다.
- **mock 전용이 아닙니다.** FastAPI 서버(`https://gridwitness-api.https.gsmsv.site`)에 연결되어 사건 등록·진단·분석·검토·마을 기록을 서버와 동기화합니다. 마을 시뮬레이터와 기본 사용량 데이터는 예시이며, 실제 장치·공공데이터와 구분해 표시합니다.
- 서버 capabilities로 CN/RU 모델과 LLM 상태를 따로 확인합니다. 준비된 나라별 모델로 분류하고 지원 범위 밖은 보류합니다. LLM이 없는 경우 서버 규칙으로 답하며 웹에서 답변 출처를 구분합니다.

폴더 한눈에 보기:

```
src/types.ts        도메인 타입 (사건, 진단, 분석 결과, 검토)
src/lib/            순수 로직 (화면 없음)
src/api/            서버 연동. 화면은 `api` 객체 하나만 부릅니다
src/components/     화면 부품, src/pages/ 화면
```

## 1. IoT: 마을 계측과 이상 탐지 (`lib/village.ts`)

### 1-1. 데이터 흐름

```
Mock 시뮬레이터 ─┐
                 ├→ 0.5초(TICK_MS)마다 측정 {v, i, relay} → anomalyScore → classify → 상태·이벤트
Web Serial 실측 ─┘
```

### 1-2. 이상 점수 (핵심 로직)

```ts
import { anomalyScore, classify, LED_A } from './lib/village'

const expected = relayOn ? 0.28 : 0           // 릴레이 상태로 정한 예상 전류(A)
const score = anomalyScore(v, i, expected)    // 0~1
const status = classify(v, i, score, relayOn) // 'NORMAL'|'WARNING'|'FAULT'|'OUTAGE'|'OFF'|'NO_DATA'
```

점수 = `max(전류 잔차, 전압 강하)`, 0~1로 자릅니다.

- 전류 잔차 = `|i − expected| / (LED_A × 2)` → LED 2개 분량 차이가 1.0
- 전압 강하 = `max(0, vMin − v) / 0.75` (예상 전류가 0보다 클 때만)
- `DEFAULT_LED_A` = 0.011 A (보정 가능한 기본값), `NOMINAL_V` = 5 V. 실제 이상 판정에는 조합별 실측 정상 전류표를 사용합니다.

`classify` 규칙 (위에서부터):

1. 릴레이 OFF인데 전류 > 0.03 A → `FAULT` (릴레이 고착 의심), 아니면 `OFF`
2. v < 1 V → `OUTAGE`
3. 점수 ≥ `THRESHOLDS.fault`(기본 0.6) → `FAULT`
4. 점수 ≥ `THRESHOLDS.warn`(기본 0.3) → `WARNING`
5. 그 외 `NORMAL`

### 1-3. 임계값 바꾸기

```ts
import { THRESHOLDS, setThresholds, resetThresholds } from './lib/village'

setThresholds({ warn: 0.25, fault: 0.5, vMin: 4.7 })
resetThresholds()
```

- `warn < fault`일 때만 localStorage(`gridwitness.thresholds.v1`)에 저장됩니다. 아니면 화면에서만 바뀌고 다음에 열면 이전 값입니다.
- `THRESHOLDS`는 항상 같은 객체라 어디서 읽어도 최신값입니다.

### 1-4. 상태 읽기·제어

```ts
import { useVillage, setRelay, injectFault, clearFault, connectSerial, switchToMock } from './lib/village'

function Panel() {
  const s = useVillage() // VillageSnapshot: v, i, p, expected, score, status, estLit, history, events ...
  return <button onClick={() => setRelay(!s.relay)}>{s.relay ? '정전 발생' : '전력 복구'}</button>
}
```

| 함수 | 설명 |
|---|---|
| `useVillage()` | 스냅샷 구독 훅 (React 전용) |
| `setChannel(id, on)` | LED 하나 끄기·켜기 (`CH <n> <0|1>`). 장치가 보고한 `ch`로 확인될 때까지 `channelPending`. `snap.canControl`이 false면 무시 |
| `setRelay(on)` | 마을 **전체** 전원. 장치가 보고한 상태로 확인될 때까지 `relayPending`. 실측은 2초 내 응답 없으면 오류 |
| `connectSerial()` / `switchToMock()` | 실측 ↔ 시뮬레이터 전환 |
| `injectFault(id, kind)` / `clearFault(id?)` | 시뮬레이터 고장 주입. kind: `OPEN` `GROUND` `SAG` `OUTAGE` `STUCK` |
| `clearSupplyFault()` | 전원 쪽 고장(SAG·OUTAGE·STUCK) 해제 |
| `setConnected(on)` | 통신 끊김 시뮬레이션 |
| `startScenario(label, profile)` / `stopScenario()` | 24시간 사용량 패턴으로 켜진 부하 수 재생 (**시뮬레이터 전용**) |
| `linkEventToCase(eventId, caseId)` | 이벤트에 등록된 사건 연결 |

주의: 실제 회로는 **전체 릴레이 1개 + 채널 릴레이 5개 + INA219 2개**입니다. 제어는 LED별로 되지만 측정은 구간(주택·가로등)까지만 됩니다. `estLit`·`zones[*].estLit`는 전류 ÷ `LED_A`로 만든 **추정 개수**이고, 어느 LED인지는 채널 점검(`lib/channelCheck.ts`)으로 확인합니다.

### 1-5. Arduino 시리얼 규약 (`lib/serial.ts`)

115200 baud, 줄 단위.

```
장치 → 웹   {"v":5.02,"i":0.281,"relay":1,"ch":[1,1,1,1,1],"vh":5.02,"ih":0.168,"vl":5.01,"il":0.113}   0.5초마다
            v·i 마을 전체 · relay 마을 전원 · ch 채널 1~5 · vh·ih 주택 구간(INA219 0x40) · vl·il 가로등 구간(0x41)
웹 → 장치   RELAY 0   /   RELAY 1   /   CH <1~5> <0|1>
```

- `parseFrame(line)`은 형식이 틀리면 `null`. 틀린 줄은 `badFrames`로 셉니다.
- Web Serial은 Chrome·Edge만 됩니다 (`serialSupported()`).
- 예제 스케치: `arduino/gridwitness_village/gridwitness_village.ino`. 릴레이가 Active-Low면 `RELAY_ACTIVE_LOW` 수정.
- 팀에서 Python 서버를 중간에 둘 계획이면, 위 JSON 줄 형식만 유지하면 웹은 그대로 씁니다.

### 1-6. IoT 사건 만들기

```ts
import { api } from './api'
const iotCase = await api.registerIotEvent({ event, actor: '홍길동' }) // event: VillageEvent
```

내부에서 `buildIotCase`(`api/iotCase.ts`)가 `IotCase`를 만들고, 서버의 `POST /energy/iot/summary`로 요약을 받습니다.

## 2. 파형: 입력 검사부터 분석까지

### 2-1. 단계

```
파일(CSV 또는 COMTRADE .cfg+.dat)
 → ingest()         읽기·해시·브라우저 입력 진단 (api/ingest.ts)
 → 서버 POST /incidents → /validation → /analysis
 → 사람 검토 POST /reviews  (AI 결과와 분리 저장)
```

CN 모델 입력 계약은 1312행 × 7채널, 4096 Hz, 50 Hz 계통입니다. RU 모델 입력 계약은 512행 × 5채널, 1600 Hz, 50 Hz입니다. 데이터셋과 실제 채널 수로 모델 계약을 고르고, 범위 밖 입력은 `LIMITED`/`REJECTED`로 진단하거나 서버에서 보류합니다. 없는 채널을 임의 생성하지 않습니다.

### 2-2. 가장 쉬운 사용법: `api` 객체

```ts
import { api } from './api'

const c = await api.registerCase({
  title: '예시 사건', file, sourceType: 'PUBLIC_DATASET', datasetId: 'xiong',
  samplingRateHz: 4096, systemFrequencyHz: 50, labelMeaning: '', actor: '홍길동',
  // cfg: File   ← COMTRADE면 .cfg를 같이 넘기고 file에는 .dat
})
const analyzed = await api.runAnalysis(c.id, 'EVENT_TYPE', '홍길동')
await api.submitReview(c.id, { reviewer: '홍길동', verdict: 'AGREE', finalJudgment: '...', additionalInvestigation: '' })
```

`GridWitnessApi` 전체: `listCases` `listActivity` `exportCases` `getCase` `registerCase` `runAnalysis` `registerIotEvent` `attachWaveform` `submitReview`.

분석 종류: 프론트엔드 타입에는 `EVENT_TYPE`(SIF·MIF·PF·TD) / `PHYSICAL_CAUSE` / `NORMAL_VS_FAULT`가 있지만, 서버 연결 모드에서는 `EVENT_TYPE`만 지원합니다. 서버 모델이 해당 데이터 계약에 맞고 준비되어 있으면 유형을 분류하며, 그 외 입력은 보류합니다. 서버 결과의 `analysis_status`, `classification`, `deferred_reasons`를 확인하세요. LLM 대화 연결 상태는 파형 분류 모델 상태를 뜻하지 않습니다.

### 2-3. 서버 없이 쓰는 순수 함수

```ts
import { parseCsv, diagnose, computeFeatures, preprocess, sha256Hex } from './lib/waveform'
import { analyzeWaveform } from './lib/faultAnalysis'
import { parseComtrade } from './lib/comtrade'

const parsed = parseCsv(text)
const { diagnosis, matrix } = diagnose(parsed, fileSize, { samplingRateHz: 4096, systemFrequencyHz: 50, sourceType: 'PUBLIC_DATASET' })
// diagnosis.status: 'ACCEPTED' | 'LIMITED' | 'REJECTED', diagnosis.issues[] 에 code·message·fix
if (matrix) {
  const feats = computeFeatures(matrix)                  // 채널별 rms, peak, crestFactor, diffRms
  const fault = analyzeWaveform(matrix, 4096, 50)        // 발생 시점, 변화량, 영상분, 지속 여부, patterns
}
```

- `analyzeWaveform`은 한 주기 전 같은 위상과 비교해 처음 크게 달라지는 지점을 찾습니다. **AI 점수와 별개인 근거값**이며 분류 결과가 아닙니다.
- `parseComtrade(cfgText, datBuffer)` → `matrix`가 `null`이면 7채널을 맞추지 못한 것입니다. `issues`와 `mapping`을 확인하세요. ASCII·BINARY·BINARY32·FLOAT32 지원.
- `toComtrade(...)`로 반대 방향 변환, `synthesize()` / `syntheticCsv()`로 테스트용 합성 파형을 만듭니다.
- 입력 시나리오 15종은 `lib/scenarios.ts`의 `INPUT_SCENARIOS`에 기대 판정과 함께 있어 테스트 입력으로 쓰기 좋습니다.

### 2-4. 입력 진단 코드 (일부)

`FILE_TOO_LARGE`(5MB 초과), `EMPTY`, `COL_MISMATCH`(7채널 아님), `RAGGED_ROWS`(열 수 불일치) 등. 모든 이슈는 `{ code, severity: 'error'|'warning'|'info', message, fix? }` 형태입니다.

## 3. 공공데이터: 한전 사용량 (`lib/publicData.ts`)

```ts
import { EXAMPLE_DATASET, getProfile, profileStats, importUsageCsv, templateCsv } from './lib/publicData'

const profile = getProfile(EXAMPLE_DATASET, '광주', 'RESIDENTIAL', 8, 'WEEKDAY') // number[24] | null
if (profile) {
  const st = profileStats(profile) // total, peak, peakHour, min, minHour, loadFactor, pattern, missingHours
}

const r = importUsageCsv(csvText, 'kepco.csv') // { dataset, issues, rowCount }
const real = r.dataset ?? EXAMPLE_DATASET
```

- CSV 열 이름: `지역,계약종별,월,요일구분,시간,사용량` (영문 별칭 `region,contract,month,daytype,hour,kwh`도 됨). 양식은 `templateCsv()`.
- 계약종별: 주택용/일반용/산업용, 요일구분: 평일/주말(휴일).
- 기본 `EXAMPLE_DATASET`은 **실제 한전 수치가 아닌 예시**입니다. 화면에 항상 그렇게 표시하세요.
- 패턴 분류(`pattern`)는 부하율(평균/최대)과 피크 시간대로 정합니다: 평탄형 / 저녁 피크 / 주간 피크 / 아침·야간 피크.
- 마을 재생: `startScenario(label, profile)`. 학습에는 쓰지 않습니다.

## 4. 서버 설정 (`lib/backend.ts`, `api/backend.ts`)

```ts
import { apiBase, setApiBase, checkHealth, useBackendHealth } from './lib/backend'
```

- 주소 우선순위: localStorage(`gridwitness.api.url`) → 빌드 시 `VITE_API_BASE` → `DEFAULT_API`. GitHub Pages는 API 직접 주소를 사용하고, 로컬/Vercel은 `/gw-api` 프록시를 사용합니다.
- 모든 호출은 `${apiBase()}/api/v1/...`. 사건 API는 등록·목록·상세·원본·진단·분석·검토·활동 내역을 지원합니다. 마을 사건·원시 이벤트는 `GET/PUT /village/records`, 현장 대화는 `/incidents/{id}/assistant`, 메모는 `/incidents/{id}/field-notes`, 공공 사용량은 `GET /energy/kepco/usage`에 연결됩니다. API 계약은 서버 문서를 기준으로 확인하세요.
- 서버 사건 메타데이터·원본·진단·분석·검토·감사 이력을 다시 받아 브라우저 캐시와 맞춥니다. 캐시는 서버별로 분리됩니다. 원본을 받을 수 없을 때만 동일 SHA-256 파일의 수동 연결을 안내합니다.
- 정적 배포는 `https://parkskin.github.io`에서 API에 직접 요청합니다. 다른 호스트에서 직접 API를 호출하려면 서버 CORS 설정에 해당 출처가 있어야 합니다. 로컬 개발은 Vite 프록시를 통해 API를 호출합니다.

## 5. 하드웨어 정의 (`lib/hardware.ts`)

부품·핀·배선(`PARTS`, `NETS`, `LOAD_LINES`)이 이 파일 한 곳에 있고, 3D 지하 배선과 설정의 배선표가 같이 씁니다. 배선을 바꾸면 여기만 고치면 됩니다.

```
5V 어댑터 → 전체 릴레이(D2, COM→NC)
  → INA219 ① 0x40 → 채널 릴레이 ①②③ (D3·D4·D5) → 주택 LED 1~3
  → INA219 ② 0x41 → 채널 릴레이 ④⑤ (D6·D7)      → 가로등 LED 4~5
  (INA219 두 개는 A4 SDA / A5 SCL 공통, 릴레이·INA219 전원은 Arduino 5V, GND 공통)
```

배선 색: 빨강 5V, 검정 GND, 초록 D2~D7, 파랑 SDA, 노랑 SCL, 주황 LED+, 회색 LED−.
LED −는 공통 GND로 그렸습니다. 실제 배선과 다르면 `NETS`와 `LOAD_LINES`를 고치세요.

## 6. 자주 하는 작업

| 하고 싶은 것 | 어디를 고치나 |

| 이상 점수 공식 변경 | `anomalyScore` / `classify` (`lib/village.ts`) |
| 새 고장 종류 추가 | `FaultKind`, `FAULT_LABEL`, `FAULT_AT_LED`, 시뮬레이터 측정부 (`village.ts`) |
| 입력 검사 규칙 추가 | `diagnose` (`lib/waveform.ts`) |
| 서버 API 추가 | `api/backend.ts` + `GridWitnessApi` 인터페이스 (`api/index.ts`) |
| 부품·핀 변경 | `lib/hardware.ts` |
| 테스트 입력 추가 | `INPUT_SCENARIOS` (`lib/scenarios.ts`) |

개발 명령: `npm run dev`(5173) · `npm run build`(타입검사 포함) · `npm run lint`(oxlint)

## 7. 주의·한계

- 이상 탐지는 **규칙 기반**(`IOT_MODEL = '규칙 기반 탐지 v0.2 (전체 전류 잔차)'`)입니다. 학습 모델이 아닙니다.
- 마을 시뮬레이터 값은 가짜(`arduino-sim-01`)입니다. 실측과 구분해서 표시하세요.
- 서버 분석은 나라별 입력 계약에 맞는 모델이 등록된 경우 분류 결과를 반환할 수 있습니다. 2026-11-10 운영 API의 읽기 확인에서는 CN/RU 모델이 `available: true`였고, 저장된 시연 사건 분석은 `completed`/`PF` 결과였습니다. 이는 전체 입력에 대한 정확도나 GPU 성능을 보증하지 않습니다. 실제 LLM 생성 성공도 별도 대화 응답의 `answer_mode`로 확인해야 합니다.
- 3D 마을은 CPU를 많이 씁니다. 기본은 30fps·정적 그림자·후처리 없음이고, "고화질" 토글에서만 무거운 효과를 켭니다.
